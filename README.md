# RSI Scanner

RSI Scanner — приложение с двумя независимыми модулями мониторинга Bybit V5: существующим RSI/EMA-скриннером USDT Linear Perpetual и Spot-монитором малоликвидных USDT-пар. Spot-модуль поддерживает постоянный Watchlist и отслеживает рост последней цены более чем на 5% за скользящие 15 минут по публичному Spot WebSocket, не дожидаясь закрытия свечи. RSI рассчитывается методом Уайлдера, EMA применяется к ряду RSI; значения индикаторов выровнены по индексам закрытых свечей, а период прогрева явно отмечен.

## Текущий состав

- Go 1.27.3;
- PostgreSQL 18;
- `pgx/v5` и пул соединений `pgxpool`;
- публичный Bybit V5 REST-клиент с пагинацией, retry и ограничением частоты запросов;
- публичный Bybit V5 Linear WebSocket для свечей 5m/15m/30m/1h, heartbeat и автоматическое переподключение;\n- публичные Bybit V5 Spot REST-каталог и ticker WebSocket; Spot-подписки отправляются пакетами по 10 тем, не более 100 тем на соединение;\n- отдельные PostgreSQL-каталог `spot_instruments` и постоянный `spot_watchlist`;
- REST backfill при каждом новом WebSocket-соединении и обнаруженном пропуске свечей;
- автоматическая синхронизация торгуемых USDT Linear Perpetual с оборотом и последней ценой;\n- мониторинг Spot USDT-пар с оборотом до $1 млн за 24 часа; из Watchlist сразу исключаются пары, уже превышающие лимит при первом появлении, а ранее наблюдавшаяся пара удерживается ещё 24 часа после пересечения лимита;\n- скользящее сравнение текущей Spot-цены с последней исторической ценой не позже границы 15-минутного окна; сигнал формируется при строго большем росте 5% на первом подходящем обновлении WebSocket;
- получение исторических свечей только после закрытия, с сортировкой по времени;
- Telegram long polling, меню, настройки, история сигналов и персональная очередь уведомлений;
- авторизация Telegram по общему паролю с сохранением доступа в PostgreSQL и ограничением попыток;
- один Go-сервис;
- Docker Compose;
- транзакционные SQL-миграции;
- хранилище пользователей, настроек, инструментов, сигналов и очереди уведомлений;
- атомарный курсор сканирования для каждой пары «инструмент + таймфрейм»;
- HTTP-проверки `/health/live` и `/health/ready`;
- JSON-логи и graceful shutdown.

Используются только публичные рыночные REST и WebSocket API Bybit V5 Linear и Spot. Приватные API, реальные ордера, торговля, Redis и Kafka не используются. WebSocket получает закрытые свечи в реальном времени; REST выполняет первичную загрузку, восстановление после переподключения и периодическую сверку.

## Схема PostgreSQL

Миграция `000001_initial_schema` создаёт:

| Таблица | Назначение |
|---|---|
| `telegram_users` | Telegram-пользователи, уникальный Telegram ID, активность и даты |
| `user_settings` | Индивидуальные параметры RSI/EMA, количество активов и флаги уведомлений |
| `user_timeframes` | Включённые таймфреймы каждого пользователя |
| `instruments` | Каталог Bybit USDT Linear Perpetual и оборот для сортировки по ликвидности |\n| `spot_instruments` | Активный каталог Bybit Spot USDT и суточный оборот |\n| `spot_watchlist` | Состояние низколиквидного Spot Watchlist, время пересечения $1 млн и исключение |
| `user_instrument_preferences` | Ручные включения и исключения инструментов |
| `signals` | Глобальные рыночные события пересечения RSI/EMA |
| `scanner_states` | Legacy-курсор общего сканера |
| `scanner_profile_states` | Независимые курсоры по инструменту, таймфрейму и RSI/EMA-профилю |
| `signal_deliveries` | Персональная доставка сигнала, попытки, lease и ошибки |

Сигнал уникален в рамках профиля индикаторов: PostgreSQL защищает комбинацию `symbol + timeframe + candle_start + direction + rsi_length + ema_length`. Одинаковое пересечение при разных периодах RSI/EMA хранится отдельно; уведомления направляются только пользователям с совпадающим профилем.

Связь «сигнал → пользователь» хранится отдельно в `signal_deliveries`. У одного рыночного события может быть несколько персональных записей доставки. История пользователя строится через эту связь.

`CommitClosedCandle` в одной транзакции продвигает курсор и записывает сигнал. Повторная или устаревшая свеча не может продвинуть курсор назад и не создаёт новый сигнал. `InitializeScannerState` не перезаписывает существующий курсор при перезапуске.

Очередь доставки поддерживает атомарный захват через `FOR UPDATE SKIP LOCKED`, аренду обработки, повторные попытки и фиксацию статуса отправки. `EnqueueSignalForEligibleUsers` учитывает включённый таймфрейм, LONG/SHORT-переключатель, индивидуальный лимит топа по обороту, режим «все инструменты» и ручные исключения/включения.

## Миграции

## Устранение неполадок

**Контейнер приложения завершается при старте.** Проверь `docker compose logs app` и `docker compose logs postgres`. Обычно причина — неверный пароль или неготовая база.

**Порт уже занят.** Измени `APP_PORT` или `POSTGRES_PORT` в `.env`.

**Readiness возвращает 503.** Проверь доступность PostgreSQL и строку подключения в конфигурации Compose.

**Изменения `.env` не применились.** Пересоздай контейнеры: `docker compose up -d --build --force-recreate`.

## Индикаторы

`internal/indicators.Calculate` принимает массив цен закрытия и периоды RSI/EMA, возвращает значения с той же индексацией, что и свечи. RSI использует начальное среднее изменение за `RSI_LENGTH` периодов и дальнейшее сглаживание Уайлдера. EMA от RSI инициализируется простым средним первых `EMA_LENGTH` значений RSI, затем применяется коэффициент `2 / (EMA_LENGTH + 1)`. До завершения прогрева `RSIReady` и `EMAReady` остаются `false`; такие точки нельзя использовать для сигналов.

Для настроек по умолчанию RSI(14) впервые доступен на индексе 14, а EMA RSI(9) — на индексе 22. При нехватке истории функция возвращает точки прогрева без ошибки.

## Реализация Bybit REST

При запуске приложение получает полный список инструментов через `GET /v5/market/instruments-info` с `category=linear`, `status=Trading` и пагинацией по `nextPageCursor`. В каталог попадают только контракты `LinearPerpetual` с `quoteCoin=USDT` и `settleCoin=USDT`. Затем запрашивается общий снимок `GET /v5/market/tickers`, из которого сохраняются `turnover24h` и `lastPrice`.

Снимок записывается в PostgreSQL одной транзакцией. Старый каталог не деактивируется, если API вернул ошибку, пустой ответ или не удалось сопоставить тикеры. Каталог обновляется при старте и далее с периодом `SCANNER_REFRESH_INTERVAL`; ошибка синхронизации логируется, приложение продолжает работать.

`GetKlines` загружает до 1000 свечей по таймфреймам `5`, `15`, `30` и `60`, сверяет время с сервером Bybit, отбрасывает незакрытую свечу и возвращает данные от старой к новой. REST-клиент также используется для начальной загрузки истории, восстановления пропущенных свечей после WebSocket-разрыва и периодической сверки.

## Ядро сканера

Сервис выбирает до `SCANNER_INSTRUMENT_LIMIT` активных инструментов по обороту за 24 часа и обрабатывает каждый включённый таймфрейм. Для каждой REST-сверки время берётся с сервера Bybit один раз и переиспользуется для всех запросов свечей. Основная обработка идёт из WebSocket только по подтверждённым закрытым свечам. После каждого подключения выполняется REST backfill; при пропуске последовательности история конкретной пары догружается через REST. Дополнительная REST-сверка запускается раз в `SCANNER_RECONCILE_INTERVAL` (по умолчанию 1 час). Старое имя `SCANNER_SCAN_INTERVAL` поддерживается как резервный alias.

При первом появлении пары «инструмент + таймфрейм» последняя закрытая свеча и рассчитанные RSI/EMA RSI сохраняются как базовая точка; исторические пересечения при первом запуске не отправляются. Далее обрабатываются только свечи новее сохранённого курсора. LONG — RSI пересекает EMA RSI снизу вверх; SHORT — сверху вниз. Пересечение проверяется только между соседними по времени свечами, поэтому пропуск в данных не создаёт сигнал.

Для каждого сигнала вычисляется контекст рынка по ADX(14), CHOP(14) и EMA(50). Дополнительно для каждого сигнала определяется рыночное состояние на старшем таймфрейме 4h: оно вычисляется по закрытым четырёхчасовым свечам теми же ADX(14), CHOP(14) и EMA(50), сохраняется в записи сигнала и выводится в Telegram над контекстом основного таймфрейма. Используются только 4h-свечи, закрывшиеся не позже сигнальной свечи; незакрытая или будущая свеча не участвует. Для расчёта требуется 52 закрытые 4h-свечи. При нехватке истории или временной ошибке Bybit старший контекст отображается как `UNKNOWN`, но само RSI-пересечение не блокируется. Боковик подтверждается, если минимум две из последних трёх закрытых свечей одновременно имеют ADX ниже `SCANNER_MARKET_ADX_SIDEWAYS_MAX` и CHOP выше `SCANNER_MARKET_CHOP_SIDEWAYS_MIN`. Восходящий или нисходящий тренд подтверждается минимум на двух из последних трёх свечей при ADX выше `SCANNER_MARKET_ADX_TREND_MIN` и соответствующем направлении наклона EMA(50). Подтверждённый `SIDEWAYS` блокирует создание сигнала и персональных уведомлений; `TRANSITIONAL` и `UNKNOWN` не блокируются. Пороговые значения можно менять через файл `.env`; при значениях по умолчанию сохраняется прежняя классификация: ADX 20, CHOP 61.8 и ADX тренда 25. Порог ADX для боковика должен быть ниже порога ADX для тренда.

Курсор, новое рыночное событие и начальные персональные записи в `signal_deliveries` фиксируются одной транзакцией PostgreSQL. Повторная обработка той же свечи останавливается по сохранённому курсору; глобальная уникальность сигнала дополнительно защищена уникальным индексом.

## Telegram

Новые пользователи по умолчанию получают только таймфрейм `30m`. Для уже зарегистрированных пользователей прежние настройки сохраняются: открой `/settings`, включи `30m` и отключи `5m`, `15m` и `60m`, чтобы получать только 30-минутные сигналы.

После настройки `TELEGRAM_BOT_TOKEN` и `TELEGRAM_ACCESS_PASSWORD` перезапусти приложение. Напиши боту `/start` и отправь общий пароль отдельным сообщением в личный чат. При успешной проверке бот запомнит авторизацию; повторно вводить пароль при каждом запуске не нужно. Миграция `000004_password_auth` потребует повторной авторизации от ранее зарегистрированных пользователей. Доступны последние сигналы, персональная история, настройки LONG/SHORT, таймфреймы, лимит пользователя, ручные включения/исключения инструментов и повторная доставка временно неотправленных уведомлений.

Команды: `/start`, `/signals`, `/history`, `/settings`, `/instruments`, `/include BTCUSDT`, `/exclude BTCUSDT`, `/reset BTCUSDT`, `/help`.

Индивидуальные RSI/EMA-периоды применяются в отдельном профиле расчёта каждого пользователя. Сканер группирует одинаковые профили, загружает свечи для общей пары «инструмент + таймфрейм» один раз и рассчитывает индикаторы отдельно для каждого профиля. Для каждого профиля сохраняется независимый курсор в `scanner_profile_states`; профильные сигналы и персональные доставки фиксируются атомарно. Это работает как при REST-сверке, так и при обработке WebSocket-свечей.\n\nПерсональный `instrument_limit` выбирает соответствующее число наиболее ликвидных активных инструментов по `turnover_24h`. Режим «все инструменты» включает весь активный каталог, ручные включения добавляют инструменты вне лимита, а ручные исключения имеют приоритет. `SCANNER_INSTRUMENT_LIMIT` используется только в legacy-режиме, когда нет активных Telegram-пользователей.\n\nВ логах REST и WebSocket поле `sideways_signals_filtered` показывает количество RSI-пересечений, которые были обнаружены, но не выпущены из-за подтверждённого бокового рынка. В персонализированном WebSocket-пути этот счётчик также включается в отчёт обработки.
