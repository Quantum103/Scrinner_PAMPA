# Volume Trader

Самостоятельный сервис на Go для получения публичных рыночных данных Bybit USDT Perpetual (Linear), анализа торгового потока, поиска LONG-сигналов, виртуального исполнения сделок (Paper Trading) и управления через Telegram. Реальное исполнение ордеров не реализовано.

## Источники данных

### REST API

Используется `https://api.bybit.com`:

- `GET /v5/market/instruments-info` — активные USDT Linear Perpetual-контракты, пагинация по `nextPageCursor`, фильтрация по типу и статусу контракта.
- `GET /v5/market/tickers` — цена, best bid/ask, 24-часовые объём и оборот, изменение цены и funding.
- Дополнительные спецификации контракта: `minOrderQty`, `qtyStep`, `minNotionalValue`, `tickSize`, лимиты рыночного ордера и интервал funding.

`volume24h` используется только для предварительной оценки ликвидности. Он не подменяет RVOL.

### Публичный WebSocket

Endpoint: `wss://stream.bybit.com/v5/public/linear`.

Для каждого символа подписки:

- `publicTrade.{symbol}` — сделки: цена, количество, сторона агрессора (`Buy`/`Sell`), время биржи и ID.
- `orderbook.50.{symbol}` — 50 уровней bid/ask.

Стакан считается доступным только после snapshot. Snapshot полностью заменяет локальную книгу; delta изменяет уровни, а размер `0` удаляет уровень. Delta без snapshot, `u=1`, регрессия sequence, пересечённый стакан и некорректные уровни инвалидируют книгу до нового корректного snapshot. Устаревшие и повторные update ID не продлевают срок актуальности.

Соединения отправляют heartbeat каждые 20 секунд, имеют read/write deadlines и переподключаются с экспоненциальной задержкой. После переподключения подписки отправляются повторно. Символы делятся на группы с ограничением конфигурации. Подписки обновляются при изменении списка инструментов.

Сообщения WebSocket обрабатываются синхронно. Для сделок дополнительно ведётся ограниченный кольцевой буфер, а повторные trade ID отбрасываются. Переполнение, переподключение или разрыв потока помечают историю как неполную. Данные такого символа нельзя использовать как готовый сигнал до восстановления непрерывной истории.

## Анализ рыночных данных

В `Store.ApplyTrades` подключён один общий анализатор на каждый символ. Каждая новая уникальная сделка обновляет все показатели; отдельные анализаторы и промежуточные lossy-каналы не используются.

- **RVOL:** объём текущей части интервала делится на средний объём такой же по длительности части предыдущих 20 завершённых минутных интервалов. Например, первые 30 секунд текущей минуты сравниваются с первыми 30 секундами каждой из 20 предыдущих минут. Нужна непрерывная история; суточный объём не участвует.
- **Taker Buy/Sell:** объёмы и доли агрессивных покупок и продаж рассчитываются по `Side` сделки Bybit.
- **Delta:** `BuyVolume - SellVolume` за окно потока.
- **CVD:** скользящая сумма Delta за `ANALYSIS_CVD_WINDOW` (по умолчанию 15 минут). История очищается при старте новой сессии, переподключении или обнаруженном разрыве данных; автоматического сброса в полночь нет.
- **Momentum:** процентное изменение цены за каждый интервал из `ANALYSIS_MOMENTUM_WINDOWS`.
- **Volume acceleration:** отношение объёма текущего окна к объёму предыдущего равного окна.
- **Orderbook:** спред между best ask и best bid, а также доступная котируемая ликвидность на заданном числе ближайших уровней каждой стороны.
- **Absorption:** потенциальное поглощение покупок — высокая доля taker-buy, их объём выше предыдущего равного окна на заданный множитель, но цена при этом почти не растёт. Это наблюдение, не торговый сигнал.

У анализатора есть статусы `ready`, `insufficient_data`, `stale`, `incomplete`, `disconnected`. При нехватке истории или недостоверном состоянии источника значение не подменяется нулём или оценкой. После переподключения база RVOL и окна CVD должны накопиться заново.

## Стратегия поиска входа (только LONG)

В `Store` после каждого принятого обновления сделки или стакана используется уже рассчитанный общий срез анализатора. Стратегия не пересчитывает RVOL/Delta/CVD отдельными обработчиками и не отправляет реальные ордера. При выполнении критериев она создаёт сигнал LONG; Paper Trading пытается открыть виртуальную позицию по текущему стакану и ограничениям риска. Сигналы сохраняются в ограниченной памяти процесса и выводятся в лог. При паузе поиска входов анализатор продолжает обновляться, а уже открытая позиция сопровождается без остановки.

Базовые фильтры:

- RVOL не ниже `ENTRY_MIN_RVOL` (по умолчанию 3).
- Доля taker-buy не ниже `ENTRY_MIN_TAKER_BUY_SHARE_PERCENT` (65%), Delta положительная, CVD положительный и растущий относительно предыдущего подтверждённого наблюдения.
- Momentum за `ENTRY_PRICE_CHANGE_WINDOW` не выше `ENTRY_MAX_PRICE_CHANGE_PERCENT` (1.5%). Окно должно присутствовать в `ANALYSIS_MOMENTUM_WINDOWS`.
- Absorption отсутствует; спред, bid/ask-ликвидность и число уровней стакана удовлетворяют заданным минимумам.
- В окне taker-потока есть минимум заданного числа сделок, а доля крупнейшей сделки не превышает `ENTRY_MAX_SINGLE_TRADE_SHARE_PERCENT`. Это ограничивает влияние одиночной крупной сделки.
- Все условия должны выполняться `ENTRY_CONFIRMATION_OBSERVATIONS` последовательных наблюдений с заданной частотой. Слишком большой интервал между наблюдениями сбрасывает подтверждение.

После сигнала действует `ENTRY_SIGNAL_COOLDOWN`. Повторная активация возможна только после указанного количества неуспешных наблюдений и завершения cooldown. При статусах анализатора, отличных от `ready`, разрыве потока, устаревшем стакане или неактуальной последней сделке вход блокируется.

### Параметры стратегии

Все значения ниже — стартовые гипотезы для тестирования, а не доказательство прибыльности.

| Переменная | По умолчанию | Назначение |

| `ENTRY_MAX_PRICE_CHANGE_PERCENT` | `1.5` | Максимальный рост цены за рассматриваемое окно, % |

| `ENTRY_MIN_BID_LIQUIDITY_QUOTE` | `5000` | Минимальная ликвидность bid в USDT |
| `ENTRY_MIN_ASK_LIQUIDITY_QUOTE` | `5000` | Минимальная ликвидность ask в USDT |

Сигнал сохраняет символ, направление, цену, время, RVOL, Taker Buy (% и объём), Delta, CVD, изменение цены и его окно, спред, ликвидность с обеих сторон и объяснение причин. Последняя оперативная история сигналов ограничена памятью процесса; показатели входного сигнала уже открытой виртуальной сделки сохраняются в SQLite вместе со сделкой.

## Paper Trading: виртуальный счёт и исполнение

Paper Trading включён по умолчанию и не отправляет реальные ордера. Он использует только публичный REST и публичный WebSocket-стакан Bybit. В \`internal/paper\` нет сетевого клиента. Публичный REST-клиент проекта выполняет только GET-запросы рыночных данных; приватный API, API-ключи и методы размещения ордеров не используются.

### Начальный риск и размер позиции

Параметры по умолчанию: 10 USDT, целевой риск 2,5% капитала, предельный риск 3% с учётом ожидаемой комиссии и проскальзывания, максимум 2x, на маржу выделяется не более 50% капитала, одна позиция, первоначальный trailing stop 2,5%.

Расчёт размера выполняется от расстояния между оценочной ценой входа и ожидаемой ценой выхода по начальному стопу. В расчёт на единицу количества входят:
- движение от фактической оценки VWAP входа до stop trigger;
- ожидаемое проскальзывание на входе и выходе;
- комиссия входа и ожидаемая комиссия выхода.

Размер дополнительно ограничивается свободной маржой, максимальной долей маржи, плечом и \`maxMktOrderQty\`. Количество округляется по \`qtyStep\`. Минимальный объём рассчитывается с учётом одновременно \`minOrderQty\` и \`minNotionalValue\`. Если минимально допустимый ордер требует расчётный риск выше 3% капитала или не помещается в лимит маржи, сделка отклоняется. Если доступной глубины не хватает на весь запланированный объём, допускается частичное исполнение, но только если фактически исполненная часть соблюдает ограничения контракта и риск.

### Виртуальное исполнение и сопровождение

- LONG-вход последовательно потребляет уровни Ask, LONG-выход — Bid.
- Средневзвешенная цена исполнения рассчитывается по фактически потреблённой глубине стакана. Настроенное проскальзывание добавляется поверх VWAP: вверх для покупки и вниз для продажи.
- Частичный выход уменьшает позицию и зарезервированную маржу. Остаток закрывается по следующим актуальным Bid; новая позиция до полного закрытия не открывается.
- Начальный stop устанавливается сразу после входа на 2,5% ниже фактической цены входа. При движении цены вверх stop следует за максимумом и никогда не опускается. Срабатывание проверяется по доступному Bid; закрытие моделируется прохождением по Bid-уровням. Цена исполнения не приравнивается автоматически к стоп-уровню.
- Дополнительный выход Order Flow Exit анализирует 4 группы признаков: снижение доли Taker Buy (или её резкое падение), агрессивные продажи вместе с отрицательной Delta, разворот CVD вниз и остановку/снижение цены. По умолчанию необходимо минимум 3 группы из 4 на 2 последовательных интервалах. Одиночная отрицательная Delta не закрывает сделку. При неготовых или устаревших данных подтверждение сбрасывается.
- После частичного срабатывания stop или Order Flow Exit менеджер продолжает закрывать оставшееся количество по следующим актуальным Bid; причина закрытия сохраняется. Take Profit не устанавливается.
- Funding применяется, если позиция пересекает \`nextFundingTime\`. Используются последние публичные \`fundingRate\` и \`markPrice\` из REST-тикера Bybit (не best Bid). Для линейного USDT-контракта сумма равна \`markPrice × quantity × fundingRate\`; положительная ставка является расходом LONG, отрицательная — поступлением. Если Mark Price устарел к моменту расчёта, settlement помечается как пропущенный, а не рассчитывается по Bid. Если funding-поля контракта отсутствуют или некорректны, новые позиции по нему не открываются.
- Комиссия входа списывается при открытии, комиссия выхода — при закрытии. Реализованный PnL включает уплаченные комиссии и funding; нереализованный PnL оценивается по текущему лучшему Bid.

Баланс, свободная и зарезервированная маржа, нереализованный и реализованный PnL, комиссии, funding и открытая позиция доступны через `Store.PaperSnapshot` и в `PaperAccount` снимка символа.

### Постоянное хранение и статистика Paper Trading

Используется **один файл SQLite всего приложения**: `APP_DB_PATH=./data/volume_trader.db`. Подсистемы Paper Trading создают собственные таблицы в этой же базе; отдельные файлы БД не создаются. Параметр `APP_DB_BUSY_TIMEOUT` задаёт ожидание блокировки SQLite (по умолчанию 5 секунд).

SQLite в режиме WAL и synchronous FULL хранит виртуальный счёт, текущую позицию, все закрытые сделки, историю капитала и обработанные ID сигналов. Счёт, позиция, закрытие сделки, комиссии, funding, equity point и запись обработанного сигнала сохраняются согласованно в транзакции. Схема имеет версию миграции; при каждом старте автоматически выполняется миграция и `PRAGMA integrity_check`. При ошибке сохранения новый вход блокируется до успешного повторного сохранения; ошибка попадает в журнал Paper Trading.

При перезапуске восстанавливаются исходный и текущий баланс, открытая позиция со stop и состоянием Order Flow, полная история закрытых сделок, кривая капитала и ID обработанных сигналов. Повторная обработка того же сигнала не создаёт вторую сделку. Восстановленная позиция продолжает сопровождаться после получения свежего стакана и новых публичных funding-данных.

Для каждой сделки сохраняются ID и причина входного сигнала, все основные показатели сигнала (RVOL, Taker Buy, Delta, CVD, Momentum, spread, bid/ask liquidity), цены и количество входа/выхода, номиналы, комиссии, проскальзывание, funding, чистый PnL, причина выхода, MFE/MAE и реализованный RR. При частичных исполнениях цена выхода рассчитывается как средневзвешенная по фактическим Bid-fill.

Статистика доступна в `AccountSnapshot.Statistics` через `Store.PaperSnapshot` / `Manager.PaperSnapshot` и всегда имеет режим `Paper Trading`. Она включает Win Rate, чистый PnL закрытых сделок, количество прибыльных/убыточных сделок, среднюю прибыль и убыток, Profit Factor, максимальную просадку, средний и максимальный реализованный RR, комиссии, проскальзывание, funding, разбивку по символам и причинам выхода. Если закрытых убыточных сделок нет, Profit Factor отмечается как бесконечный (`infinite_profit_factor=true`). Средний убыток отображается отрицательным числом.

MFE/MAE оцениваются по лучшему Bid после входа относительно фактической VWAP входа и исходного количества позиции. Кривая капитала записывается при изменениях счёта и не реже одного раза в пять секунд при поступлении обновлений стакана. Максимальная просадка рассчитывается по сохранённой equity curve и учитывает нереализованное движение открытой позиции.

Для сборки SQLite-драйвера с CGO в Linux/WSL нужен C-компилятор (например, `build-essential` в Ubuntu). На Windows рекомендуется запускать проект внутри WSL2.

| `PAPER_ORDER_FLOW_PRICE_STALL_MAX_RISE_PERCENT` | `0.02` | Допустимый небольшой рост цены, который ещё считается остановкой, % |
| \`PAPER_FEE_RATE\` | \`0.00055\` | Расчётная комиссия за сторону, доля от номинала |
| \`PAPER_SLIPPAGE_BPS\` | \`5\` | Расчётное проскальзывание на исполнение, базисные пункты |

Значения комиссии и проскальзывания — только стартовые предположения симуляции, не фактические тарифы аккаунта. Их следует заменить на свои реальные значения. Старые \`TRADING_FEE_RATE\` и \`SLIPPAGE_BPS\` поддерживаются как fallback, если новые \`PAPER_*\` переменные не заданы.

### Параметры общей базы данных

| Переменная | По умолчанию | Назначение |
|---|---:|---|
| `APP_DB_PATH` | `./data/volume_trader.db` | Единый файл SQLite для приложения |
| `APP_DB_BUSY_TIMEOUT` | `5s` | Ожидание блокировки SQLite |


## Telegram: управление и уведомления

Бот использует официальный HTTP Bot API через long polling. Сторонний SDK не требуется. Telegram необязателен для запуска сканера, но для удалённого управления и уведомлений задай токен и allowlist в `.env`:

```env
TELEGRAM_BOT_TOKEN=токен_от_BotFather
TELEGRAM_ALLOWED_USER_IDS=123456789,987654321
TELEGRAM_DAILY_LOSS_LIMIT_PERCENT=5
```

Токен выдаётся через `@BotFather`. В allowlist указываются **числовые Telegram user ID**, а не username или номер телефона. Пользователь должен один раз открыть личный чат с ботом и нажать Start, иначе Telegram не разрешит боту первым отправить ему сообщение. Команды в групповых чатах не обрабатываются. Любой ID, отсутствующий в allowlist, не может читать состояние или менять настройки. Токен не записывается в SQLite или логи и хранится только в переменной окружения.

Команды в личном чате:

| Команда | Действие |
|---|---|
| `/start` | Кратко объясняет режим и команды |
| `/status` | Состояние процесса, число WebSocket-соединений Bybit, инструменты и пауза входов |
| `/balance` | Виртуальный баланс, equity, свободная/зарезервированная маржа, PnL и затраты |
| `/position` | Текущая виртуальная позиция, цена, объём, stop, MFE/MAE и Order Flow |
| `/stats` | Статистика Paper Trading по сделкам, монетам и причинам закрытия |
| `/trades` | Последние пять закрытых виртуальных сделок |
| `/pause` | Останавливает только поиск новых входов |
| `/resume` | Возобновляет поиск новых входов, если не действует дневной лимит убытка |

**Пауза не останавливает Position Manager.** После `/pause` обработка каждого актуального стакана, обновление Funding, Trailing Stop и Order Flow Exit продолжаются для открытой позиции. Подтверждение новых входов сбрасывается; после `/resume` стратегия накапливает наблюдения заново.

Бот уведомляет о запуске, каждом подтверждённом LONG-сигнале, открытии виртуальной позиции, значимом повышении Trailing Stop, закрытии и результате сделки, потере/восстановлении WebSocket, ошибках REST/WS рыночных данных и достижении дневного лимита убытка. Уведомление о закрытии содержит gross PnL, комиссии, проскальзывание, funding, чистый Paper PnL и новый виртуальный баланс. Уведомления отправляются через отдельную очередь, чтобы медленный Telegram API не блокировал обработку рыночного WebSocket.

Дневной лимит по умолчанию равен 5% equity на начало текущего UTC-дня; он настраивается `TELEGRAM_DAILY_LOSS_LIMIT_PERCENT`. Дневной PnL считается по изменению equity (реализованный и нереализованный результат). При достижении лимита новые входы автоматически блокируются до следующего UTC-дня. Уже открытая позиция не закрывается автоматически и продолжает сопровождаться. Ручная команда `/resume` не может снять блокировку дневного лимита. Если Telegram не настроен или выключен, бот и его дневной монитор не запускаются.

## Установка и запуск

Требуется Go 1.23 или новее. SQLite использует CGO-драйвер: в Ubuntu/WSL установи C toolchain:

```sh
sudo apt update
sudo apt install -y build-essential
```

Клонируй репозиторий и подготовь конфигурацию:

```sh
git clone https://github.com/Quantum103/Scrinner_PAMPA.git
cd Scrinner_PAMPA
cp .env.example .env
go mod download
```

Открой `.env`. Для рыночных данных достаточно публичных endpoint Bybit — API-ключи не нужны. Проверь `BYBIT_REST_URL`, `BYBIT_PUBLIC_WS_URL`, `MARKET_DATA_ENABLED=true` и параметры анализа/входов из разделов выше.

Для Telegram создай бота через `@BotFather`, впиши выданный токен в `TELEGRAM_BOT_TOKEN` и один или несколько **числовых** Telegram user ID в `TELEGRAM_ALLOWED_USER_IDS` через запятую. Перед запуском открой личный чат с ботом и нажми Start. Если токен и allowlist пустые, приложение запускает Paper Trading без Telegram управления.

Запуск:

```sh
go run ./cmd/volume-trader
```

Для сборки исполняемого файла:

```sh
go build -o ./bin/volume-trader ./cmd/volume-trader
./bin/volume-trader
```

В PowerShell скопируй шаблон командой `Copy-Item .env.example .env`, внеси значения в `.env` и запусти `go run ./cmd/volume-trader`. Приложение читает переменные из окружения; если не используешь оболочку, которая загружает `.env` автоматически, экспортируй нужные пары KEY=VALUE перед запуском.

SQLite-файл создаётся автоматически по `APP_DB_PATH`. Каталог `data` исключён из Git; не удаляй БД, если нужно сохранить Paper Trading account и историю сделок.

## Ограничения первой версии

- Только публичные рыночные данные Bybit и виртуальное исполнение LONG. Реальных ордеров, приватного API и API-ключей Bybit нет.
- Нет Take Profit; выходы выполняются по Trailing Stop, подтверждённому Order Flow либо вручную через код (Telegram не содержит ручной команды торговли).
- Качество результатов Paper Trading зависит от глубины и частоты публичных данных, выбранных допущений комиссий и проскальзывания. Виртуальные результаты не являются реальной прибылью и не гарантируют будущий результат.
- Оперативные окна анализатора и накопленная история сигналов не переживают перезапуск; счёт, открытая позиция, закрытые сделки, метрики исполнений и equity history восстанавливаются из SQLite.
